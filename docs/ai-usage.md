- 2026-11-11 · An AI assisted architecture plan proposed a separate Hono service, an admin app, PgBouncer, Valkey, idempotency keys and capability flags · Kept one Next.js app with two database roles and deferred the rest to "next version" (spec 0001) · Too much infrastructure for a 72 hour first version, and it bypassed the ports and adapters layout.
- 2026-11-11 · The same plan guarded overlaps with a unique index on (room, date, slot) · Replaced it with an exclusion constraint on a time range · The unique index lets 10:00 to 12:00 and 11:00 to 13:00 both succeed.
- 2026-11-11 · The plan put row level security on every table · Rooms stay shared with no RLS, and availability goes through a function that returns busy intervals only · Otherwise a company could not see that a room is taken.
- 2026-11-11 · The default flow let the same agent that wrote a feature also write its tests · Changed to: tests ship with each slice (written from the spec, critical proofs first), then a separate fresh agent that did not write the code tries to break it · Tests written by the code's author tend to copy its assumptions. The second agent may only test behaviours named in spec 0001, the scope row or the brief, reports anything else as a finding, never edits production code or weakens tests, and runs against real Postgres. Used on the risky slices only (database, booking, cancel, metrics, cookie).
- 2026-11-11 · A first answer from the assistant said the operator could use ADR 0003's owner role · Switched to a dedicated read only `BYPASSRLS` role plus `FORCE` row level security · The owner can also write and change the schema.
- 2026-11-11 · The assistant opened a branch for every commit, chores included, then collapsed everything onto `main` alone · Kept `main` for the setup and released versions, `develop` for integration with small changes committed on it directly, and `feat/*` branches from `develop` only for new features · One branch per commit is noise, but a single branch loses the release boundary the brief's commit history should show.
- 2026-11-11 · For the database foundation, `/test` sent a fresh agent to write a second, adversarial suite on top of the 40 integration tests the slice already shipped with · Stopped it and kept the existing tests plus the manual `/check verify` run · The brief asks for automated tests of the critical behaviours, not full coverage; overlap, concurrency, isolation, roles and seeds were already proven against real Postgres, and the hours go further on the missing screens.
- 2026-11-11 · Spec 0001 (written with the assistant) set the session cookie to `userId.signature`, yet the scope asks for a 401 on an expired cookie · Changed to `userId.expiresAt.signature`, with the expiry signed and checked on the server · Only the browser enforces `maxAge`, so a copied cookie would have stayed valid forever. Found by `/develop` before writing the code.
- 2026-11-11 · `/develop` wrote a verify step for the error contract expecting a 403 from a POST to `/api/v1/rooms` with a foreign Origin · Moved the step to feature 5 (POST `/api/v1/bookings`) and recorded the feature 4 verify as PASS · `/check verify` ran it and got 405: the route has only `GET`, so Next refuses the POST before the Origin check runs.
- 2026-11-11 · To save tokens while iterating on e2e, the assistant proposed reusing a `next dev` server on the local database instead of a fresh container per run · Kept a fresh, seeded throwaway Postgres for every e2e run and dropped only the `next build`: `E2E_NEXT=dev` makes `e2e/web-server.ts` start `next dev`, and one spec runs at a time · Starting and seeding the container is cheap and keeps the data known; the build and long logs were the real cost. The e2e gate still runs on `next start`. (Later replaced by named e2e suites; the `E2E_NEXT=dev` switch was removed.)
- 2026-11-11 · The assistant recommended `agentRules: false` in `apps/web/next.config.ts` to stop `next dev` from writing its "This is NOT the Next.js you know" block into `apps/web/AGENTS.md` · Kept the block and commit it with the work · It is maintained by Next itself, so it stays correct for the installed version, and any agent sees it even without the project skills.
- 2026-11-11 · During the book a room build the assistant ran the e2e suite itself after most UI changes, chased a flaky test, took screenshots and ran ad hoc API scripts, then proposed its own iteration plan · Ported soporte-it's practices instead: an "Iterating cheaply" section in AGENTS.md, named e2e suites (`pnpm check:ai --gate=e2e --suite=bookings|shell`), the dropped scoped verification rules, and the user runs e2e from a command the assistant hands over · Most of the time went to verification and side work; soporte-it had already solved this.
- 2026-11-11 · Spec 0004 as first written modeled a block only as maintenance, and left a person without a company unable to book · Changed after review: a block is any closure the operator imposes (maintenance, holiday, private event) and stays invisible to companies, and a person who works alone is a client of kind `individual` with one member · A block answers "why can nobody use this room", not just repairs, and one tenant rule keeps isolation, overlap and metrics the same for a person and a company.
- 2026-11-11 · The assistant had worded the operator permission as "can never book" and proposed a 3 option menu for individuals · Clarified that only the operator database login has no write on `booking` (members still book, the operator reads and blocks), and chose the one member company over the other options · The first wording read as if the operator could not use the product, and a grant alone also let the operator insert an `operator` user, so a trigger now refuses it.

- 2026-11-12 · Wiring the operator dashboard template to the metrics API, the assistant recommended hiding the template values with no source (the 90 day daily chart among them) · The engineer chose to add `GET /api/v1/operator/metrics/daily` so the daily chart stays, and to hide only goal, attendance, reassigned, plans, room floor and type, and export · The daily series is a real metric with the same definitions as room usage; the hidden values need data the model does not hold yet.
